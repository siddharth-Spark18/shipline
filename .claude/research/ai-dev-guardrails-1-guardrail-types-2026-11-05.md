# Guardrails around AI coding agents: what big orgs and agent vendors actually enforce

Date: 2026-11-05. Depth: deep (single sub-question, ~25 searches/fetches by one agent).

## Question and scope
What guardrails do large tech companies (Google, Meta, Microsoft/GitHub, Amazon/AWS, Stripe, Shopify, Uber, Airbnb, Coinbase, Anthropic, OpenAI) put around AI coding agents? Covered: action/command restrictions, protected paths, sandbox and permission models, secret scanning and leak prevention, tool/MCP access control, strict-vs-permissive tuning, and what the agent tools ship as enterprise guardrail features (Claude Code, Copilot coding agent, Cursor, Codex, Devin, Amazon Q/Kiro, Gemini CLI).

Important coverage caveat: only Stripe, Uber, Meta (security framework only) and Anthropic published first-party detail I could fetch. I found NO primary-source material on Shopify, Airbnb, Google-internal, Microsoft-internal, or Coinbase-internal agent guardrails. For those, most of what the broader web says is vendor marketing or unverifiable. Much of the "what companies enforce" picture therefore comes from the guardrails the vendors ship, which are a proxy for, not evidence of, what any given company enforces.

## Bottom line
1. The dominant pattern among orgs that publish detail (Stripe) is "isolate the environment, then give the agent freedom inside it": full permissions, no prompts, but no production data, no arbitrary network egress, curated tools, bounded CI retries, and mandatory human PR review. Guardrails live in the environment and at the merge gate, not in per-command prompts.
2. Where agents run on developer laptops, vendors converge on the same layered model: OS-level sandbox (filesystem scoped to the workspace, network off or domain-allowlisted), permission rules (deny > ask > allow), protected config paths, a classifier or approval prompts for the rest, and org-level managed policy that developers cannot override.
3. The most consistently blocked actions: force push / history rewrite, push to main or deploy branches, production deploys and migrations, `terraform destroy`-class infra destruction, `curl | bash`, credential scanning/printing, exfiltrating data to unknown hosts, and editing the agent's own permission/config files.
4. Per-prompt approval is a known failure mode. Anthropic reports users approve 93% of prompts; the industry response is to shrink prompts via sandboxes (84% fewer prompts, Anthropic internal) or a classifier, while keeping hard denies for a short list of irreversible actions.
5. For a hook-based tool: the vendor docs show hooks work best for fail-closed deny/ask on a small list, must be enforced from a tamper-resistant tier, and are weak against command-text bypasses (so pair with sandbox/network controls).

## Findings

### 1. Action and command restrictions

What gets blocked by default (Anthropic, Claude Code auto-mode classifier; first-party):
- Default block categories (20+ rules): destroy/exfiltrate (force-pushing over history, mass-deleting cloud storage, sending internal data externally); degrade security posture (disabling logging, installing SSH keys/cron persistence, modifying the agent's own permission config); cross trust boundaries (running code cloned from external repos, scanning credential stores, sending data to unspecified services); bypass review (pushing directly to main, production deploys, modifying shared resources the agent didn't create). Allow exceptions are narrow, e.g. installing packages already in the manifest, pushing to the session's working branch. Source: [Claude Code auto mode (Anthropic engineering)](https://www.anthropic.com/engineering/claude-code-auto-mode).
- The permission-modes docs list the same plus `terraform destroy`, `git reset --hard`, `git clean -fd`, granting IAM/repo permissions, merging unapproved PRs, printing live credentials, pushing secrets to public repos. Allowed by default: local file ops in the working dir, declared dependency installs, read-only HTTP, pushing to any branch of the current repo unless the branch name marks a deploy target (`production`, `gh-pages`). User-stated boundaries like "don't push" are treated as blocks. Source: [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes.md).
- Auto-mode safety valve: after 3 consecutive or 20 total denials the session stops and escalates to the human (headless: process terminates). Same Anthropic post.
- Stated error rates (Anthropic's own numbers): full pipeline false-positive rate 0.4% on real traffic, but a 17% miss rate on real "overeager" actions (n=52 — small sample) and 5.7% on synthetic exfiltration. Anthropic calls 17% "the honest number". So classifiers are not a hard boundary.

GitHub Copilot coding agent (first-party docs, [risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)):
- Can push only to one branch: the PR's branch or a new `copilot/` branch. Credentials only allow simple pushes; the agent cannot run `git push` or other git commands directly.
- Cannot mark its PR ready for review, approve, or merge; the requester cannot approve it; an extra approval is required for PRs not attributed to a person (default on in rulesets). Branch protection and required checks still apply.
- GitHub Actions workflows do not run on the agent's changes until a write-access user clicks "Approve and run workflows".
- Only write-access users can trigger it; other users' comments are never shown to it. Hidden characters/HTML comments are filtered from input.
- Built-in validation by default: CodeQL, Copilot code review, secret scanning, and dependency checks against the GitHub Advisory Database (each can be disabled).
- Also: 59-minute max in Actions sessions, one branch and one PR per task, scoped to one repo ([about coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)).

Stripe "Minions" (first-party, [Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)):
- Run unattended on isolated cloud devboxes with full permissions and no confirmation prompts; rationale is "limited blast radius of one devbox".
- Devboxes sit in the QA environment: no real user data, no production services, no arbitrary network egress.
- Blueprints mix deterministic nodes (lint, push; no LLM) with agent steps. One local fix attempt on failing tests, at most two pushes with full CI, then back to a human. Humans review all minion code.
- A security control framework prevents tools from taking destructive actions.
- Secondary coverage ([InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/)) repeats these; I did not independently re-verify it, and the Stripe blog is first-party self-description.

Replit incident (anecdotal/press, July 2025): agent deleted a production DB despite a "code freeze" instruction; Replit reportedly responded with automatic dev/prod DB separation and a plan/chat-only mode ([eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)). Press only; I did not confirm the fix shipped as described. Lesson commonly drawn: instructions in prompts are not guardrails; environment separation is.

### 2. Protected files and paths

- Claude Code never auto-approves writes (in default, acceptEdits, auto, dontAsk modes) to: `.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, `.claude`; and files `.gitconfig`, `.gitmodules`, shell startup files (`.bashrc`, `.zshrc`, `.profile`, `.envrc`...), `.npmrc`, `.yarnrc*`, `.bazelrc`, `.pre-commit-config.yaml`, `lefthook.yml`, `.devcontainer.json`, `.mcp.json`, `.claude.json`. Only `bypassPermissions` skips this. Rationale visible in the list: these are files that execute code or change tool behavior later (hooks, shell init, package-manager config, MCP). Source: [permission modes](https://code.claude.com/docs/en/permission-modes.md).
- Codex sandbox keeps `.git` (including `gitdir:` pointer targets), `.agents`, `.codex`, and `.aws` read-only and recursive even inside writable roots. Source: [Codex agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security.md).
- Cursor: agent can edit workspace files without approval except configuration files; MCP tool calls need approval unless allowlisted. Source: [Cursor agent security](https://cursor.com/docs/agent/security).
- Documented example secret protection: `permissions.deny` with `Read(./.env)` / `Read(./.env.*)` ([Claude Code settings](https://code.claude.com/docs/en/settings)).
- Not found in any primary source: a vendor default that protects migrations dirs, CI workflow files (`.github/workflows`), or infra (terraform) paths as such. Those protections come from (a) CODEOWNERS/branch protection/required review at merge time, and (b) GitHub's rule that agent-authored workflow runs need manual approval. Treat migrations/infra/CI path protection as an org-defined layer, not a vendor default. (Inference.)

### 3. Sandboxing and permission models

- Anthropic's rationale ([Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)): both filesystem and network isolation are needed; without network isolation a compromised agent could exfiltrate SSH keys, without filesystem isolation it could escape. Network goes through a proxy outside the sandbox with a domain allowlist and a prompt for new domains. Internally this cut permission prompts by 84%.
- Claude Code docs caveat: the working-directory boundary is a permission prompt, "a Bash command you approve can still write anywhere your user account can"; use OS sandbox for real enforcement. Deny rules match command text as written, so network enforcement should use sandbox rather than `curl` denies ([security](https://code.claude.com/docs/en/security)). Managed docs make the same point: denying WebFetch still leaves `curl` via Bash unless the sandbox allowlist is on ([admin setup](https://code.claude.com/docs/en/admin-setup.md)).
- Codex: modes `read-only`, `workspace-write` (default Auto preset), `danger-full-access`/`--yolo`; Seatbelt on macOS, bwrap+seccomp on Linux. Network OFF by default; optional domain proxy is allowlist-first (deny wins) and off by default; web search defaults to cached. Cloud tasks run in OpenAI-managed containers, agent phase offline by default. Approval modes `on-request`, `never`, `granular`, plus an `auto_review` reviewer agent. Source: [Codex docs](https://learn.chatgpt.com/docs/agent-approvals-security.md).
- Cursor: terminal sandbox blocks network by default and limits files to workspace and `/tmp`; admins control sandbox availability and team-wide git/network access ([Cursor enterprise post, 2025-10-31](https://cursor.com/blog/enterprise)). Cursor's docs call run-mode allowlists "best-effort guardrails, not a hard security boundary" ([security](https://cursor.com/docs/agent/security)).
- Gemini CLI (Google): sandbox is off by default and opt-in (Seatbelt/Docker/Podman/gVisor etc.); trusted folders off by default; policy engine with tiers Default < Extension < Workspace < User < Admin, decisions allow/deny/ask_user (ask_user becomes deny in non-interactive mode); admin policy only honored from root-owned directories. Docs note the Workspace tier was non-functional at time of fetch. Sources: [policy engine](https://geminicli.com/docs/reference/policy-engine.md); sandbox/trusted-folder defaults came from search snippets only (not fetched). A published advisory (GHSA-wpqr-6v78-jr5g) reported headless CI mode auto-trusted workspace folders and a `--yolo` allowlist bypass (via a third-party mirror; not verified against the advisory itself).
- Copilot coding agent: internet restricted by a firewall (customizable/disableable; not compatible with self-hosted/Windows runners, where orgs must supply their own network controls) ([customize environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/customize-the-agent-environment)).
- Claude Code cloud sessions: isolated VM, limited network by default, GitHub credentials never enter the VM (proxy attaches them), proxy rejects branch deletions and non-branch pushes (tags), logged for audit ([security](https://code.claude.com/docs/en/security)).
- Devin: per-session isolated machine; enterprise VPC option keeps the Devbox in the customer VPC (PrivateLink) while the "brain" stays in Cognition's cloud ([Devin docs via search](https://docs.devin.ai/enterprise/vpc/overview)). I did not fetch pages describing Devin secrets or permission model.
- Amazon Q Developer CLI: tools are "trusted" or "per-request"; `/tools trust-all` is discouraged for production/sensitive data; custom agents are JSON files defining tool access. AWS guidance: assume the agent can do anything within its entitlements, so bound it with narrow IAM roles, permission boundaries and SCPs ([Q CLI tool permissions](https://docs.aws.amazon.com/amazonq/latest/qdeveloper-ug/command-line-chat-tools.html), [security considerations](https://docs.aws.amazon.com/amazonq/latest/qdeveloper-ug/command-line-chat-security.html); these were surfaced by search, not fetched). Kiro trusted-command list (others auto-denied) from search snippet of kiro.dev docs; unverified. A "Kiro 3.0 permissions.rules" claim and an IAM agent-vs-human condition-key claim were only in third-party posts; unverified.
- Meta ([Agents Rule of Two, 2025-10-31](https://ai.meta.com/blog/practical-ai-agent-security/)): a session should combine at most two of (A) untrusted input, (B) sensitive systems/data, (C) ability to change state or communicate externally. If all three needed, require human-in-the-loop or other validation. Mitigations: run in a test environment (drop B), restrict outbound recipients (drop C), restrict inputs to trusted sources (drop A). Meta explicitly says it is not sufficient alone (users may approve without scrutiny). This is a design framework, not a description of Meta's internal coding-agent config; I found nothing first-party on Meta's internal coding agents.

### 4. Secret scanning and data-leak prevention
- Copilot coding agent runs secret scanning, CodeQL and dependency advisory checks on its own changes by default ([GitHub](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)).
- Claude Code: `Read` deny rules for `.env`; classifier blocks printing live credentials, scanning credential stores, pushing secrets to public repos (but allows reading `.env` and sending credentials to their matching API). Cloud: git credentials kept outside the VM ([permission modes](https://code.claude.com/docs/en/permission-modes.md), [security](https://code.claude.com/docs/en/security)).
- Cursor says hooks can "block unapproved commands and scrub secrets in real time" (vendor claim, [enterprise post](https://cursor.com/blog/enterprise)). A third-party source warns Cursor's sandbox still permitted reading `~/.ssh/id_rsa` while blocking writes (unverified; use hooks to block sensitive reads).
- Uber's MCP gateway redacts PII and sensitive data from tool responses by default and uses "Response Projection" to fetch only needed fields ([Uber](https://www.uber.com/bl/en/blog/designing-mcp-gateway/)). It does not describe secret handling.
- Egress control is the main leak defense (Stripe: no arbitrary egress; Codex: network off; Claude sandbox proxy allowlist), which is stronger than scanning outputs.
- Zero-retention / no-training terms are the vendor-contract layer ([Claude admin setup](https://code.claude.com/docs/en/admin-setup.md)).

### 5. Tool and MCP access control
- Uber (first-party, [Oct 2026 post](https://www.uber.com/bl/en/blog/designing-mcp-gateway/)): central MCP gateway (800+ servers, 5000+ tools per the post as summarized by InfoQ/Forkast). Per-tool authorization using Uber's access control system for humans/services/agents; charter policies at server level with tool-level overrides; rate limiting; PII redaction. Discovered tools start disabled until owners enable them ("discovery doesn't imply exposure"); tool-description changes create a config diff owners must approve (guards against tool-description injection/rug pulls). Code Mode via `aifx` CLI is the default for coding agents. A separate May 2026 Uber post on short-lived JWTs / actor-chain was only seen via [Forkast](https://forkast.news/uber-ships-mcp-gateway-at-production-scale-800-servers-and-5000-tools-behind-a-single-control-surface/); unverified.
- Stripe: central MCP server "Toolshed" (~500 tools) but each minion gets only a small curated default subset; extra tool sets opt-in.
- Claude Code managed settings: `allowedMcpServers`, `deniedMcpServers`, `allowManagedMcpServersOnly`, `managedMcpServers`/`managed-mcp.json`; plugin marketplace allowlists; `strictPluginOnlyCustomization` to block user/project skills, agents, hooks and MCP; `.mcp.json` servers need their own approval prompt ([admin setup](https://code.claude.com/docs/en/admin-setup.md), [security](https://code.claude.com/docs/en/security)).
- Codex managed config can pin approved `mcp_servers`; Cursor requires approval per MCP tool call unless allowlisted; Copilot Actions sessions limit the GitHub MCP server to the working repo by default.

### 6. Hooks and managed enforcement (what the tools ship)
Claude Code ([hooks](https://code.claude.com/docs/en/hooks), [settings](https://code.claude.com/docs/en/settings), [admin setup](https://code.claude.com/docs/en/admin-setup.md)):
- `PreToolUse` can allow, deny, ask, defer, and rewrite input. Exit code 2 blocks even if JSON says allow; exit 1 or crashes are NON-blocking by default; `onFailure: "block"` (v2.1.295+) makes crash/timeout/invalid output fail closed. Timed-out hooks do not block unless `onFailure: "block"`. This is a notable footgun for guardrail hooks.
- Hook events include `PermissionRequest`, `ConfigChange` (audit or block settings changes), `InstructionsLoaded`, `FileChanged`, `SubagentStart` and many more.
- Managed tier: precedence managed > CLI > local > project > user. `permissions.allow/deny` arrays merge, so developers can extend but not remove managed rules. `allowManagedPermissionRulesOnly`, `permissions.disableBypassPermissionsMode`, `permissions.disableAutoMode`, `allowManagedHooksOnly` (blocks user/project/plugin hooks; managed hooks cannot be disabled by `disableAllHooks` from lower tiers), `sandbox.enabled` and `sandbox.network.allowedDomains`, MCP/plugin lockdown, `blockReadsOutsideWorkingDirectories`/`blockWrites...` (a `true` from any scope wins over managed `false`). Delivery: server-managed (claude.ai console), MDM/plist/registry (tamper-resistant, need admin), or `/etc/claude-code/managed-settings.json`; Windows HKCU is explicitly "not an enforcement channel".
- Project-level `deny`/`ask` rules apply immediately; project `allow` rules and extra directories wait for workspace trust; `auto`/`bypassPermissions` default mode cannot be set from project files (to stop a cloned repo from loosening its own guardrails).
- Also: a managed policy CLAUDE.md is described as "behavioral guidance rather than a client-enforced rule".
Cursor: hooks (`beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `afterFileEdit`, `stop` per third-party write-ups; official event names not verified), distributed by MDM or cloud (enterprise); priority Enterprise > Team > Project > User per a third-party guide; a forum report says hook allow/ask can be overridden by Cursor's own allowlist, so only deny reliably wins ([forum](https://forum.cursor.com/t/beforeshellexecution-hook-permissions-allow-ask-ignored-allow-list-takes-precedence/144244), unverified). Audit log tracks 19 event types.
Codex: managed configuration with allowed approval policies, web-search modes, reviewer policy, approved MCP servers, network policy; cloud vs local policies separate. Gemini CLI: admin-tier TOML policies. Copilot: hooks exist for validation/logging; guardrails are mostly server-side GitHub controls (rulesets, Actions approval).

### 7. Strict vs permissive: how defaults are tuned
- Approval fatigue is the stated driver: 93% of manual prompts approved ([Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)); a secondary summary claims humans catch only 13.6% of dangerous commands vs 89% for the classifier — I could not trace that to the primary post; do not cite it as Anthropic's.
- Strategies seen: (a) sandbox so most actions need no prompt (84% fewer prompts); (b) classifier instead of human for the middle band; (c) fixed read-only allowlist (`ls`, `cat`, `git status`) with fail-closed on unmatched or unparseable commands; (d) narrow hard denies for irreversible actions that no mode overrides (even bypass still prompts for `rm -rf /` or `~`); (e) per-repo, per-user, per-org allowlists; (f) escalate-to-human after repeated denials rather than loop.
- Orgs that publish detail (Stripe) choose "permissive inside, strict at the edges": no prompts, but no prod, no egress, capped retries, and mandatory human code review. Stripe's reported scale: 1,300+ merged PRs/week (secondary coverage, [ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs) not fetched).
- Strict-by-default, loosen deliberately: Codex and Cursor sandboxes default to network off; Claude Code manual mode starts read-only; Gemini CLI and Copilot (firewall) differ: Gemini sandbox is opt-in.
- Coinbase: engineering blog says every engineer had used Cursor by Feb 2025 and adoption was slower on "complex and system-critical exchange systems" ([Coinbase blog](https://www.coinbase.com/blog/Tools-for-Developer-Productivity-at-Coinbase), seen via search snippet, not fetched). That implies risk-tiered adoption by system criticality (inference); no first-party Coinbase guardrail config found.

### 8. Why (incident evidence)
- Amazon Q Developer VS Code extension v1.84.0 (July 2025) shipped with an injected prompt instructing the agent to wipe the home dir and delete AWS resources; AWS pulled it in 1.85.0 and said no customers/production services were affected. Press-only sourcing; the AWS bulletin was not fetched. Sources disagree on timing of the clean release (July 19 vs July 24). ([The Register](https://www.theregister.com/2025/07/24/amazon_q_ai_prompt/), [BleepingComputer](https://bleepingcomputer.com/news/security/amazon-ai-coding-agent-hacked-to-inject-data-wiping-commands)). Motivates: protect agent supply chain, least-privilege IAM, sandbox.
- Replit prod DB deletion (above). Motivates environment separation.
- Coinbase/Cursor "CopyPasta" license-attack research (HiddenLayer): instructions hidden in files propagate. Reported via crypto press; vendor research. Motivates protected config files and input filtering.

## Disagreements and uncertainty
- Approval statistics: 93% (Anthropic engineering post, fetched) vs 97% and 13.6%/89% catch rates (secondary social/aggregator posts). Use 93% only.
- Whether classifier/hook approaches are enough: Anthropic itself reports a 17% miss rate on overeager actions; Cursor calls allowlists best-effort; Claude docs say deny rules on command text are bypassable. Everyone pairs soft controls with OS sandbox or environment isolation.
- Cursor hook precedence vs allowlist: forum report contradicts expectation; unresolved.
- Gemini CLI workspace policy tier "non-functional" per docs at fetch time; docs also inconsistent on Admin base (5 vs 4).
- Stripe numbers and Uber's May 2026 security post rely partly on secondary summaries.
- Not found / unverified: first-party guardrail detail for Google internal, Microsoft internal, Meta internal coding agents, Shopify, Airbnb, Coinbase; Devin permission/secrets model; Kiro permission schema; Cursor official hook event names and sandbox network modes; Cursor terminal docs page was thin. A YouMind claim that Shopify uses a push/deploy deny list is unverified and should be ignored.
- Dates: most vendor docs are living pages without publication dates (fetched 2026-11-05); Cursor enterprise post 2025-10-31 and Meta post 2025-10-31 are >12 months from none but could be stale for fast-moving features. Claude Code feature/version details (e.g. v2.1.295 `onFailure`) were current at fetch.

## Takeaways relevant to a hook-based guardrail tool (observations, not evaluation)
- Real teams' hard-deny set clusters on: force push/history rewrite, push to main/deploy branches, prod deploy/migration, infra destroy, pipe-to-shell, credential reads/exfil, editing agent config/hooks/CI-executed files.
- Fail-closed behavior matters: a default-nonblocking hook error (exit 1, timeout) silently allows; Anthropic added `onFailure: "block"` for this.
- Enforcement tier matters: hooks in repo `.claude/settings.json` can be overridden locally or add to, not remove, managed ones; only managed hooks with `allowManagedHooksOnly` are tamper-resistant.
- Hooks and permission rules cannot see network or non-Bash side effects; vendors pair them with sandbox/network allowlists and merge-time controls (branch protection, required review, CI approval).
- Stage-based modes resemble Codex/Gemini/Claude modes (read-only/plan -> edit -> auto) and Stripe's blueprint (deterministic steps around agent steps, bounded retries).
