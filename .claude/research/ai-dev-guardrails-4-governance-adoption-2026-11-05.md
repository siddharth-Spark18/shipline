# Governance and rollout of AI-assisted development at scale (guardrail tooling adoption)

Date: 2026-11-05. Depth: deep (single researcher, cross-checked where possible).

## Question and scope

How do large tech companies and regulated/enterprise engineering orgs govern and roll out AI-assisted development at scale? Sub-topics: org-wide policy (approved tools, data handling, centrally enforced vs per-repo config); monorepo vs polyrepo agent configuration; compliance/audit (SOC 2, finance, healthcare); measuring adoption and impact; rollout strategy; why developers resist/abandon guardrail and workflow tooling and what made adoption stick. Context: reader is building an open-source team tool adding workflows and guardrails to Claude Code. Public web only. Vendor material is labeled.

## Bottom line

1. Mature governance is layered: a centrally enforced floor (managed settings/rulesets that users cannot weaken), repo-committed conventions owned by the people who own the code, and personal overrides that can only add. Claude Code and GitHub Copilot both implement this "floor + additive layers" model.
2. The strongest evidence for what makes AI tooling pay off is organizational, not tool-specific. DORA 2025: AI amplifies existing strengths and weaknesses; it raised throughput but still correlated with lower delivery stability. A clearly communicated AI stance, small batches, strong version control, quality internal platforms are the named amplifiers.
3. Productivity evidence is mixed and measurement is hard. Google's RCT showed ~21% faster on one task (wide CI); METR's early-2025 RCT showed 19% slower for experienced OSS devs, then METR said its later study is unreliable because developers refuse to work without AI. Perception diverges from measurement. Do not promise a number; measure delivery and stability outcomes plus developer experience.
4. Compliance for AI-written code is mostly "same change-management gate as human code, plus attribution and tamper-resistant logs." I found no AICPA/regulator guidance specific to AI-generated code; the SOC 2 material is vendor/practitioner opinion.
5. For adoption of guardrail tooling specifically: the best primary evidence (Google static analysis, Anthropic's own permission-prompt data) says trust is lost through noisy/false-positive output and approval fatigue, and kept through low false-positive rates, in-workflow delivery, fast feedback, and a named owner who ships a working first experience. Mandates produce resentment and metric gaming (anecdotal/secondary).

## Findings

### 1. Org-wide policy: approved tools, data handling, centrally enforced settings

- Claude Code (vendor docs, current): managed settings take precedence over user/project settings and are delivered via the claude.ai admin console (server-managed), MDM plist/registry, or a file on disk; array settings like `permissions.allow/deny` merge so developers can extend but not remove managed entries. Enforceable controls include permission rules, `allowManagedPermissionRulesOnly`, disabling bypass-permissions mode, sandboxing with network allowlists, MCP allowlists, plugin marketplace restrictions, `strictPluginOnlyCustomization` (skills/agents/hooks only from plugins or managed settings), hook restrictions, login/org enforcement, provider restrictions, model restrictions, version floors, and telemetry opt-out. A managed-policy CLAUDE.md is explicitly "organization-wide behavioral guidance rather than a client-enforced rule", i.e. advisory vs enforced is a documented distinction. Source: [Anthropic admin setup](https://code.claude.com/docs/en/admin-setup.md).
- Data handling: on Team/Enterprise/API/cloud plans Anthropic states it does not train on code or prompts; ZDR is available to qualified Enterprise accounts; a gateway is recommended for request-level audit logging or routing by data sensitivity (same page). Note the trade-off: sessions through a gateway are not eligible for the HIPAA configuration ([HIPAA setup](https://code.claude.com/docs/en/hipaa-setup.md)). Those are vendor self-statements.
- DORA's first of seven AI capabilities is a "clear and communicated AI stance" (expectations, support for experimentation, which tools are permitted); notably the benefit "doesn't depend on the specific content of the policy, only that the stance is clear and communicated." Source: [Google Cloud: DORA AI Capabilities Model](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model) (Google/DORA, first-party research).
- GitHub's parallel model: enterprise rulesets are a floor that org/repo rulesets can add to but "never override"; instructions exist at org and repo level; CODEOWNERS plus "require review from Code Owners" is the path-based ownership control. The page does not define precedence between org and repo instructions. Source: [GitHub Docs: maintain codebase standards](https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/govern-at-scale/maintain-codebase-standards) (vendor docs).

### 2. Monorepo vs polyrepo configuration

- Documented Claude Code pattern (vendor docs): root CLAUDE.md for repo-wide rules, per-directory CLAUDE.md (loaded on demand) owned by each directory's owner, path-scoped rules in `.claude/rules/` as the centralized alternative, per-directory skills, and `claudeMdExcludes` for other teams' packages. Project `.claude/settings.json` is NOT inherited from parent directories, so each area's settings must be self-contained, and worktree sessions need a second copy at the root. Source: [Large codebases guide](https://code.claude.com/docs/en/large-codebases.md).
- The same page states the scaling failure mode: "Conventions drift, files go stale, and no one owns the root." The suggested fix is to move conventions to plugins in an internal marketplace owned by a platform team, installable via managed settings, versioned and namespaced; plus telemetry (`skill_activated` OTel event) to find unused skills. This is the polyrepo answer too: a shared plugin/marketplace rather than copy-pasted files.
- Review config on a schedule: every 3-6 months or after major model releases, retiring hooks/skills that worked around old limitations ([Anthropic blog on large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start); vendor).
- DORA 2025: architecture matters: loosely coupled teams with fast feedback gain from AI; tightly coupled, slow-process teams see little or no benefit ([Google Cloud DORA 2025 announcement](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)).
- Gap: I found no independent (non-vendor) study comparing monorepo vs polyrepo agent-config outcomes. Everything above on config layout is vendor documentation.

### 3. Compliance and audit

- SOC 2: the change-management criterion (CC8.1) is technology-neutral, so AI-initiated changes need the same authorization, testing and approval evidence; practitioners recommend a human approver who is not the author, the same CI gate on AI and human PRs, a distinct identity per agent, and logs the agent cannot alter; the AI vendor's SOC 2 report does not replace your own controls. Sources: [Tianpan blog](https://tianpan.co/blog/2026-05-05-ai-generated-code-compliance-attestation-gap), [hoop.dev](https://hoop.dev/blog/soc-2-for-ai-coding-agents-guardrails-for-code-and-data-access/), [DEV article](https://dev.to/coppersundev/building-a-soc2-audit-trail-for-ai-assisted-dev-1851). Labeled: practitioner and vendor opinion; no official AICPA or auditor guidance found. The main risk named is nominal human review when AI output outpaces reviewers.
- Healthcare: Claude Code documents a HIPAA configuration for Enterprise orgs with a BAA: some features are off (WebFetch, cloud sessions, Remote Control, feedback), Anthropic credentials are stripped from hooks/MCP env, local session data retention is the org's responsibility (`cleanupPeriodDays`, `claude purge`), and only direct Enterprise-account connections qualify ([HIPAA setup](https://code.claude.com/docs/en/hipaa-setup.md); vendor).
- Audit visibility: OpenTelemetry export of sessions/tools/tokens, analytics dashboard and APIs, Compliance API activity types on Enterprise, optional gateway audit log with IdP identity ([admin setup](https://code.claude.com/docs/en/admin-setup.md)).
- Financial services: thin evidence. Reported examples (CIBC Copilot to 1,800+ devs per a [Deloitte case study](https://www.deloitte.com/ca/en/who-we-are/story/impact/cibc.html), vendor-partner source claiming 10-14% productivity gain; BNY and Goldman claims from secondary/vendor blogs). Common governance theme: defined who can use which tools on what data, how outputs are validated. I found no primary regulator guidance and nothing on JPMorgan/Citi; treat bank claims as unverified.

### 4. Measuring adoption and impact

- DORA 2025 (about 5,000 respondents; Google research): 90% use AI at work; over 80% believe it raised productivity; about 30% have little or no trust in AI-generated code; AI adoption now positively associated with throughput and product performance but still negatively with delivery stability, because extra change volume exposes weak downstream controls. Leader recommendations include clarifying AI policy, connecting AI to internal context, fortifying safety nets, investing in the internal platform. 90% of orgs have an internal platform; quality platforms correlate with unlocking AI value. Source: [Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report). Seven capabilities per [DORA model post](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model): clear AI stance, healthy data ecosystems, AI-accessible internal data, strong version control, small batches, user-centric focus, quality internal platforms. Survey-based, correlational.
- Google enterprise RCT (96 engineers, internal logging-service task, summer 2024): ~21% less time on task, but wide CI; secondary summaries disagree on significance and subgroup effects. Source: [arXiv 2410.12944](https://arxiv.org/abs/2410.12944) (abstract; I did not read the full paper).
- GitHub/Accenture field experiment: +8.69% PRs, +15% merge rate, 81.4% installed the extension the day they got a license ([GitHub blog](https://github.blog/news-insights/research/research-quantifying-github-copilots-impact-in-the-enterprise-with-accenture/); vendor-authored, via search snippet only; I did not fetch the page). The academic pooled study (Cui et al., Dell/Accenture/Microsoft) reports larger gains at Microsoft and bigger benefits for less experienced devs (search summary only).
- METR early-2025 RCT: 16 experienced OSS devs, 246 tasks, tasks 19% longer with AI (CI +2% to +39%); developers predicted 24% faster and afterwards believed ~20% faster. Source: [METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/). METR later (Feb 2026): late-2025 estimates of -18% time (10 returning devs, CI -38% to +9%) and -4% (47 new devs, CI -15% to +9%), but calls them "very weak evidence" and a likely lower bound because developers declined to work without AI and 30-50% withheld tasks; METR is redesigning the study. Source: [METR update](https://metr.org/blog/2026-02-24-uplift-update/). Implication: classic RCTs are now hard to run; the perception-measurement gap is real.
- Telemetry vs outcomes: Faros AI (vendor telemetry, 10,000+ devs, July 2025) reports high-adoption teams finish 21% more tasks and merge 98% more PRs but PR review time rises 91%, PR size 154%, bugs per dev 9%, with no org-level delivery improvement ([Faros](https://www.faros.ai/blog/ai-productivity-paradox-report-2025); figures via secondary summaries, primary report not read). Consistent in direction with DORA's stability finding.
- Frameworks: DX Core 4 unifies DORA, SPACE, DevEx into speed / effectiveness / quality / impact ([DX](https://getdx.com/research/measuring-developer-productivity-with-the-dx-core-4/); vendor framework, search snippet only). For a Claude Code tool, practical signals: OTel/analytics for usage, plus DORA four keys incl. change failure rate and rework, review time, and a developer survey. Caution from LeadDev: acceptance rate and lines generated reward the wrong thing, and execs rated rollouts successful far more than employees did (75% vs 45%, per a survey cited secondhand) ([LeadDev](https://leaddev.com/ai/ai-coding-mandates-are-driving-developers-to-the-brink)).
- Trust: Stack Overflow 2025 survey: 3.1% highly trust AI output, 29.6% somewhat trust, 45.7% distrust; top frustration "almost right but not quite" 66%; debugging AI code more time-consuming 45.2%; agents used daily by 14.1% ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai)).

### 5. Rollout strategy

- Anthropic's own field guidance (vendor, drawn from customer rollouts): a dedicated owner (minimum viable: a single DRI for settings, permission policy, plugin marketplace, CLAUDE.md conventions), usually in developer-experience; infrastructure ready before broad access so the first experience is productive; a cross-functional working group (engineering, infosec, governance) early; start with approved skills, required code review and limited access, expand as confidence grows; "bottoms-up adoption generates enthusiasm but can fragment without someone to centralize what works"; bundle skills/hooks/MCP in plugins so new users get the same context day one ([Claude blog](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)).
- GitHub's rollout docs (vendor): phased rollout gives visibility into adoption, satisfaction, and blockers before going to everyone; champions/"AI manager" group; org-wide strategy statement from leadership; lunch-and-learns and office hours; measure trial success by adoption, engagement, and early usage ([GitHub rollout resource](https://resources.github.com/enterprise/copilot-adoption-rollout-impact/), [docs](https://docs.github.com/en/copilot/tutorials/roll-out-at-scale); summarized from search results/index page, details not fully read).
- Opt-in vs mandated: reported mandates (Coinbase, Shopify, Microsoft) come from secondary coverage; the Coinbase firing claims and Microsoft claims are unverified, and one viral Microsoft claim was found uncorroborated. LeadDev reports leaders tracking usage/leaderboards and developer frustration, and suggests: let developers choose tools, leaders learn the tools hands-on, set company-level goals with team flexibility, managers define granular metrics. Anecdotal/trade press, not controlled evidence. METR's own data hint that heavy users will refuse to give up tools they value, i.e. real value drives retention better than mandates.

### 6. Why developers resist or abandon guardrail/workflow tooling, and what made it stick

- Google static analysis (CACM 2018, primary but I could only access abstract/secondary summaries): "effective false positive" means developers took no positive action, and developers, not tool authors, decide what is a false positive; false positives and untrustworthy results are a main reason engineers ignore tools; careful workflow integration is key; earlier FindBugs integration attempts (2006, 2009, 2011) failed; Tricorder succeeded with an in-review integration, a "NOT USEFUL" feedback button, continuous monitoring of false-positive rates, and analyzers owned and tuned by authors ([CACM via search](https://cacm.acm.org/magazines/2018/4/226371-lessons-from-building-static-analysis-tools-at-google/pdf), [Google Research abstract](https://research.google/pubs/lessons-from-building-static-analysis-tools-at-google/), [Tricorder ICSE 2015 PDF](https://www.cs.umd.edu/class/spring2019/cmsc414/papers/tricorder-building-a-program-analysis-ecosystem.pdf)). The commonly repeated "~10% false-positive ceiling" could not be verified in any text I could read; do not cite it as Google's rule without checking the paper.
- Approval fatigue (Anthropic engineering): users accept 93% of permission prompts, so prompts stop being a real control; Anthropic built classifier-based auto mode as a middle between sandboxing (safe but needs ongoing configuration) and skipping permissions (no protection) ([Anthropic engineering](https://www.anthropic.com/engineering/claude-code-auto-mode); vendor self-report, measurement method not given). Lesson for guardrail design: deterministic boundaries set up front (sandbox, deny lists, managed allowlists) beat per-action prompts.
- Slowness: practitioner posts and forum threads (anecdotal, no survey data) say slow pre-commit hooks (over ~5 seconds is one author's threshold) get bypassed with `--no-verify`, so keep local checks fast and make CI the enforcement point ([DEV Community](https://dev.to/singebob/git-hooks-not-everything-is-worth-blocking-for-361f), [gist](https://gist.github.com/brennanMKE/dc0b346a56e3a4b73d7f80fe303f6032)). Claude Code docs echo this: managed Claude.md is advisory, hooks are enforcement; sandbox needed because deny rules on tools can be bypassed via Bash ([admin setup](https://code.claude.com/docs/en/admin-setup.md)).
- Verification burden: Stack Overflow's "almost right" frustration and DORA's 30% low-trust figure indicate that tooling which reduces the cost of verifying AI output (tests, small batches, review aids) addresses the actual pain.
- What stuck (synthesis, partly inference): (a) owner who maintains it and prunes it (Anthropic, Google), (b) works on day one with zero config, (c) delivered inside existing workflow (PR/CI, review) rather than a separate step, (d) low noise with a visible feedback channel, (e) org floor enforced centrally while teams add stricter local rules, (f) measured by outcomes developers care about rather than usage leaderboards.

### Implications for an open-source Claude Code team tool (inference)

- Fit the native layering: ship as a plugin/marketplace (the officially documented central-distribution path) that can be pre-installed via managed settings, rather than inventing a parallel config system; respect that settings are not inherited by subdirectories.
- Distinguish advisory (CLAUDE.md, skills) from enforced (hooks, permissions, CI checks) and document which is which; make CI the backstop for anything a developer can bypass locally.
- Emit audit evidence compatible with SOC 2 narratives: who/which agent/which model/what gate passed, in a location the agent cannot modify. Support OTel.
- Keep hooks fast and false-positive rate low, provide a one-step "not useful" feedback path and count it; ship a staged mode (warn then block) to support pilots.
- Provide a DRI-friendly admin experience: one place to see what is deployed, which rules/skills get used, and which are stale.

## Disagreements and uncertainty

- Productivity: Google RCT (+21% faster, wide CI, secondary sources disagree on significance), Accenture (+8.69% PRs, vendor), METR (-19%, then unreliable follow-up), Faros (more throughput but more review time and bugs; vendor). These measure different things (task time, PR counts, telemetry) and differing tool generations. METR's selection-bias disclosure suggests newer tools help more than the 2025 slowdown implies, but this is METR's own cautious inference, not a result.
- DORA: perceived productivity (80%+) vs stability harm vs 30% low trust is correlational survey data.
- Subgroup effects (seniority) conflict across summaries of the Google paper; I did not read the full paper.
- Not fetched or only via search snippets: GitHub/Accenture, Faros primary report, DX Core 4, Deloitte/CIBC, Cui et al., full Tricorder/CACM text (PDF fetches returned binary and could not be parsed). Claims from those carry that caveat.
- Mandates: Coinbase/Shopify/Microsoft details come from secondary coverage and were not verified against primary reports.
- Not found: independent evidence on monorepo vs polyrepo agent config; official regulator or AICPA guidance on AI-generated code; hard data on guardrail-tool abandonment rates for AI-agent hooks specifically; controlled comparison of opt-in vs mandated AI rollout.
